# 管理画面UI仕様

## 1. 位置付け

本書は、シフト管理Webアプリにおける管理画面のUI、操作、状態表示、保存、配布、認可に関する仕様を定義する。

管理画面の実装前に、必ず以下を確認すること。

- `AGENTS.md`
- `docs/specs/01_requirements.md`
- `docs/specs/02_database.md`
- `docs/specs/03_staff_ui.md`
- `docs/specs/images/`配下の管理画面参考画像
- 現在のルート、Controller、Service、Policy
- 現在のBlade、CSS、JavaScript
- 現在のMigration、Model、Seeder

本書と既存実装に差異がある場合は、既存コードを無条件に破棄せず、差異と影響範囲を報告する。

本書、業務仕様、データベース仕様、参考画像が矛盾する場合は、勝手に判断せずユーザーへ確認する。

`_ng`画像は、シフトに不備があり、修正が必要で配布できない正式な画面状態を表す。

主に以下の確認基準として使用する。

- 警告対象のスタッフ名
- 警告対象の日付
- 警告対象のセル
- 警告色
- 警告アイコン
- 不備内容の案内
- 配布ボタンの無効状態
- 修正が必要であることの表示
- 通常状態との表示差分

画像だけを根拠に、仕様書にない機能や処理を追加してはならない。

操作仕様、認証、認可、保存処理、配布処理、入力チェックについては、以下を優先する。

シフト編集は自動保存のみとし、保存ボタンは設けない。

必要に応じて参考画像の保存ボタンと同じ位置を、保存待ち、保存中、保存済み、保存失敗等の保存状態表示に使用する。

## 4. ユーザー区分と認可

認可は、画面上でボタンを隠すだけでなく、Controller、Service、Policy等のサーバー側でも必ず実施する。

ログイン識別子にはメールアドレスだけを使用する。

`users.email`は組織をまたいでシステム全体で一意とする。

### 4.1 staff

スタッフ権限だけを持つユーザーは、管理画面を利用できない。

管理画面のURLを直接開いた場合も、403または適切な画面へ遷移させる。

### 4.2 shift_manager

シフト管理者は、`store_shift_manager`で有効な担当店舗についてのみ、以下を利用できる。

- 店舗別シフトの閲覧
- 店舗別シフトの編集
- 店舗別シフトの配布
- 担当店舗情報の編集
- 担当店舗のシフトパターン管理
- 主所属店舗が担当店舗であるスタッフ情報の追加・編集

担当外店舗については、一覧、URL、APIのいずれからも編集できないようにする。

管理画面・スタッフ別では、選択した担当店舗へ有効な所属があるスタッフを表示する。

重複勤務を確認するため、そのスタッフの対象月における全店舗のシフトを閲覧できる。

担当外店舗のシフトは閲覧専用とする。

ユーザー権限およびシフト管理者の担当店舗割り当ては変更できない。

### 4.3 system_admin

システム管理者は、全ての`active`店舗について以下を利用できる。

- 閲覧
- 編集
- 配布
- 店舗管理
- スタッフ管理
- 権限管理
- シフト管理者の担当店舗管理

`inactive`店舗については、過去データを閲覧できるが、新規シフト作成、シフト編集、配布はできない。

店舗情報と店舗状態は、`active`と`inactive`の両方を管理できる。

ユーザー権限およびシフト管理者の担当店舗割り当てを変更できるのは、システム管理者だけとする。

### 4.4 複数権限

一人のユーザーが複数権限を持てる。

スタッフ兼シフト管理者の場合も、管理画面で操作できる店舗は担当店舗だけとする。

## 5. 共通レイアウト

管理画面には、現在位置と操作対象が分かる共通ヘッダーまたはナビゲーションを設ける。

最低限、以下を表示する。

- 管理画面であること
- ログイン中ユーザー名
- 対象店舗
- 対象年月
- 店舗別画面とスタッフ別画面の切り替え
- 必要な管理メニュー
- ログアウト手段

担当店舗が複数あるシフト管理者とシステム管理者は、対象店舗を切り替えられる。

店舗切り替え時は、権限を再確認する。

URLやリクエストの店舗IDだけを信用しない。

## 6. 対象月

シフト画面は月単位で表示する。

対象月は年と月を検証し、DB上では月初日として扱う。

例：

```text
2026-07-01
```

前月・翌月への移動、月選択UI、初期表示月は参考画像と現在の実装を優先する。

以下を正しく扱う。

- 28日
- 29日
- 30日
- 31日
- うるう年
- 月初が日曜日
- 月末が土曜日
- 年をまたぐ月移動

特定月専用の日付HTMLや固定配列を使用しない。

## 7. 管理画面・店舗別シフト編集

### 7.1 目的

対象店舗・対象月の最新下書きを、スタッフ行と日付列の表形式で編集する。

この画面をシフト入力の主画面とする。

### 7.2 表示対象

表示するスタッフは、対象店舗への有効な所属を持つユーザーとする。

新規シフト作成と編集の対象店舗は、`status = active`でなければならない。

システム管理者が`inactive`店舗の過去データを開いた場合は、閲覧専用とする。

スタッフ行は原則として以下の順に並べる。

1. `store_user.display_order`
2. スタッフ名
3. ユーザーID

順序はリロードごとに変化しないようにする。

### 7.3 表の構成

最低限、以下を表示する。

- スタッフ名列
- 日付列
- 曜日
- 各スタッフ・各日付のシフトセル
- シフト入力ボタン
- 保存状態
- 下書き最終更新日時
- 配布状態
- 最終配布日時
- 配布ボタン
- 警告表示
- 人数チェック結果
- スタッフ単位の月間計

日付列は対象月の日数に応じて動的に生成する。

土曜日、日曜日、祝日、当日の見せ方は、参考画像と既存UIを維持する。

月間計は、選択店舗の対象月における下書き`shifts`だけをスタッフ単位で集計する。

表示項目は、勤務時間、A〜Eの各登録件数、総数とする。

総数にはA〜E、研、有を含め、研と有はA〜Eの各登録件数へ含めない。

勤務時間は`work_minutes`を合計し、累積時間の`HH:MM`形式で表示する。

24時間を超えても折り返さず、2250分は`37:30`と表示する。

### 7.4 シフト入力モード

シフトコードのボタンを選択すると、入力モードになる。

入力モード中にセルをクリックすると、選択中のシフトコードを入力する。

入力モードは、以下のいずれかまで維持する。

- 別のシフトコードを選択する
- 選択中のボタンを再度押して解除する
- 明示的な入力解除操作を行う

シフトコードの例：

- A
- B
- C
- D
- E
- 研
- 有

画面に表示する入力ボタンは、対象店舗の`store_shift_patterns.is_active = true`のものだけとする。

### 7.5 セル内の複数シフト

同一スタッフ・同一日・同一店舗に複数シフトを登録できる。

セル内の複数シフトは、`sequence`順に表示する。

各シフトは、個別のラベルまたはチップとして表示する。

連続2シフトを1件にまとめたり、後のシフトを上書きしたりしない。

新規入力は、現在の最大`sequence`より後ろへ追加する。

各シフトを個別に削除できるようにする。

追加と削除は自動保存する。

ドラッグによる並べ替えは今回実装しない。

順番を変更する場合は、対象シフトを削除して再入力する。

同一コードの複数登録は許可する。

各シフト追加操作へ一意な`entry_uuid`を付与する。

意図的な追加ごとに新しいUUIDを発行し、通信再試行時は同じUUIDを再利用する。

同じ`entry_uuid`の追加は一度だけ処理し、二重送信による意図しない重複登録を防止する。

### 7.6 削除

既存シフトを削除できる。

削除操作は、誤操作を避けられる形にする。

削除後も自動保存の対象とする。

個別削除後は、同一セルに残ったシフトの`sequence`を1からの連番へ詰め直す。

削除と`sequence`の詰め直しは、同じトランザクション内で行う。

削除が保存に失敗した場合は、画面上の状態を消さず、失敗表示と再試行手段を提供する。

## 8. 自動保存

### 8.1 基本動作

保存ボタンは設けず、シフト入力・変更・削除後に自動保存する。

参考画像内の保存ボタンは再現しない。

複数変更は、500〜1000ms程度のdebounce後にまとめて送信する。

通信には`fetch()`を使用してよい。

### 8.2 保存状態

画面には、少なくとも以下の状態を表示する。

- 未変更
- 保存待ち
- 保存中
- 保存済み
- 保存失敗
- 競合発生

表示文言の例：

```text
保存中…
保存しました
保存に失敗しました
他の更新と競合しました
```

保存成功後は、保存日時または更新状態を分かる形で表示する。

### 8.3 保存失敗

保存失敗時に、ユーザーが入力した内容を即座に破棄しない。

以下を提供する。

- エラーメッセージ
- 再試行
- 必要に応じた再読み込み
- 競合時の案内

通信失敗時に成功表示を出してはならない。

### 8.4 楽観ロック

`draft_version`を使用する場合、画面が保持するバージョンとDB上の最新バージョンを比較する。

一致しない場合は無条件に上書きせず、競合として返す。

競合時は、ユーザーに再読み込みまたは差分確認を促す。

### 8.5 シフト追加の二重送信防止

クライアントは、意図的なシフト追加操作ごとに新しい`entry_uuid`を発行する。

通信失敗等による同じ追加操作の再試行では、同じ`entry_uuid`を再利用する。

サーバーは同じ`entry_uuid`の登録を一度だけ処理し、既に処理済みの場合は新しいシフトを追加しない。

同一コードを意図的に複数登録する場合は、追加操作ごとに異なる`entry_uuid`を使用する。

## 9. 管理画面・スタッフ別シフト閲覧

### 9.1 目的

対象月のシフトをスタッフ単位で確認し、店舗をまたぐ勤務や個人別の勤務状況を確認する。

この画面は閲覧専用とする。

シフト編集は店舗別画面で行う。

### 9.2 表示対象

シフト管理者は、選択した担当店舗へ有効な所属があるスタッフを表示できる。

重複勤務を確認するため、表示対象スタッフについては、対象月の全店舗のシフトを表示する。

担当外店舗のシフトは閲覧専用とし、編集できないようにする。

シフト管理者と関係のないスタッフを取得してから画面上で隠す方式にしない。

システム管理者は、全スタッフ・全店舗のシフトを閲覧できる。

### 9.3 表示内容

最低限、以下を表示する。

- 対象年月
- スタッフ名
- 日付
- 曜日
- シフトコード
- 店舗名
- 警告表示
- 配布可否
- 最終更新日時
- 最終配布日時
- 店舗別編集画面への移動手段

対象月・スタッフ単位で、以下の月間計を表示する。

- 勤務時間：表示対象シフトの`work_minutes`合計
- A〜E：各コードの登録件数
- 総数：A〜E、研、有を含む全シフト登録件数

スタッフ別画面では、画面に表示している全店舗の下書き`shifts`をスタッフ単位で集計する。

研と有は総数に含めるが、A〜Eの各登録件数には含めない。

勤務時間は累積時間の`HH:MM`形式で表示し、24時間を超えても折り返さない。

2250分は`37:30`と表示する。

同一日に複数シフトがある場合は、各シフトを1件として集計する。

同日に複数シフトがある場合は、すべて表示する。

同一日・異なる店舗の勤務がある場合は、対象スタッフ名と対象日を警告表示する。

### 9.4 編集禁止

スタッフ別画面のセルをクリックしても、シフトを直接編集しない。

編集が必要な場合は、対象店舗・対象月の店舗別編集画面へ移動する。

シフト管理者は、担当店舗の店舗別編集画面にだけ移動できる。

担当外店舗のシフトには編集操作を表示せず、直接URLやAPIを指定した場合も編集を拒否する。

## 10. 重複勤務の警告

### 10.1 判定

以下の場合を重複勤務とする。

```text
同一スタッフ
かつ同一日
かつ異なる店舗が2件以上
```

同一店舗内の連続2シフトは重複勤務にしない。

### 10.2 表示

重複勤務がある場合は、少なくとも以下を警告表示する。

- 対象スタッフ名
- 対象日
- 対象セル
- 関係する店舗
- 修正が必要であること
- 配布できないこと

`kanri_staffbetsu_ng.png`および`kanri_tenpobetsu_ng.png`を、警告状態の正式な表示例として参照する。

色だけに依存せず、アイコン、文言、枠線等を併用する。

### 10.3 保存と配布

重複勤務があっても下書き保存は許可する。

重複勤務が1件でも残っている場合は、配布を許可しない。

## 11. 人数チェック

### 11.1 無効

`staffing_check_mode = disabled`の場合は、人数判定を行わない。

画面の判定欄には`－`を表示する。

配布前の人数検証対象外とする。

### 11.2 固定人数

`staffing_check_mode = fixed_total`の場合は、日別の出勤スタッフ数と`required_staff_count`を比較する。

同一スタッフが同日に同一店舗で複数シフトを持つ場合も、人数は1人として数える。

シフト件数ではなく、重複しないスタッフ数を集計する。

### 11.3 表示

不一致の日は、少なくとも以下を分かる形で表示する。

- 対象日
- 必要人数
- 実際の人数
- 不足または超過
- 配布できないこと

人数不一致が残っている場合は、配布を許可しない。

---

## 12. 配布状態

管理画面には、店舗・対象月単位の配布状態を表示する。

想定状態：

- 未配布
- 配布済み
- 再配布が必要
- 修正が必要で配布不可
- 保存中または未保存変更あり

判定例：

```text
published_versionがNULL
→ 未配布

published_version = draft_version
→ 配布済み

published_version < draft_version
→ 再配布が必要
```

配布後に下書きを変更した場合は、スタッフ画面へ即時反映せず、「再配布が必要」と表示する。

## 13. 配布

### 13.1 配布ボタン

配布ボタンは、配布権限を持つユーザーだけに表示する。

シフト管理者は担当店舗だけ配布できる。

システム管理者は全ての`active`店舗を配布できる。

### 13.2 配布可能条件

以下をすべて満たす場合に配布可能とする。

- 自動保存が完了している
- 保存失敗が残っていない
- 競合が解消されている
- 重複勤務がない
- 人数チェックの不備がない
- 対象店舗が`active`である
- その他の配布前必須チェックを通過している

### 13.3 配布不可状態

不備がある場合は、配布ボタンを無効化する。

ボタンを無効化するだけでなく、理由を画面上に表示する。

例：

```text
シフトに修正が必要なため配布できません。
```

不備の一覧または対象箇所へ移動できる案内を提供する。

### 13.4 強制配布

強制配布機能は設けない。

クライアント側でボタンを有効化されても、サーバー側で再検証して拒否する。

### 13.5 配布中

配布処理中は二重送信を防止する。

配布ボタンを一時的に無効化し、処理中であることを表示する。

配布成功後は、以下を更新する。

- 配布状態
- 最終配布日時
- 配布者
- `published_version`
- 再配布必要表示

---

## 14. 店舗管理

### 14.1 店舗一覧

システム管理者は`active`と`inactive`を含む全店舗を表示する。

システム管理者向け店舗一覧では、状態を指定して有効・無効を絞り込めるようにする。

シフト管理者は、担当店舗のうち`active`店舗だけを表示する。

最低限、以下を表示する。

- 店舗名
- 店舗コード
- 状態
- 表示順
- 人数チェック方式
- 必要人数
- 担当シフト管理者
- 編集手段

### 14.2 店舗編集

シフト管理者は、担当店舗の許可された項目だけを編集できる。

システム管理者は全項目を編集できる。

想定項目：

- 店舗名
- 店舗コード
- 状態
- 表示順
- 人数チェック方式
- 固定必要人数

店舗状態は以下の2種類とする。

- `active`（有効）
- `inactive`（無効）

`suspended`、`closed`は現時点では使用せず、保存も許可しない。

`inactive`店舗では、新規シフト作成、シフト編集、配布を許可しない。

`inactive`へ変更しても、過去の下書きシフトと公開シフトは削除しない。

システム管理者は、`inactive`店舗の過去データを閲覧できる。

`inactive`店舗は通常の店舗選択肢へ表示しない。

担当シフト管理者の割り当て変更は、システム管理者だけが行える。

店舗コードの重複、人数の負数、無効な状態値を保存しない。

### 14.3 削除

通常の削除はSoft Deleteまたは状態変更で扱う。

関連シフトがある店舗を物理削除しない。

- メールアドレス
- 在籍状態
- 主所属店舗
- 所属店舗
- 権限
- 編集手段

シフト管理者には、主所属店舗が担当店舗であるスタッフだけを表示する。

システム管理者には全スタッフを表示する。

### 15.2 スタッフ追加・編集

想定項目：

- 氏名
- メールアドレス
- 在籍状態
- 主所属店舗
- 所属店舗
- 店舗内表示順
- 権限

シフト管理者は、主所属店舗が担当店舗であるスタッフだけを追加・編集できる。

ユーザー権限およびシフト管理者の担当店舗割り当てを変更できるのは、システム管理者だけとする。

シフト管理者は、`staff`、`shift_manager`、`system_admin`の権限および担当店舗割り当てを変更できない。

シフト管理者向け画面では、権限項目と担当店舗割り当て項目を非表示または閲覧専用にする。

主所属店舗は、有効な所属店舗の中から選択する。

組織をまたぐ場合も含め、メールアドレスの重複をシステム全体で許可しない。

### 15.3 パスワード

パスワードの初期設定や再設定は、安全な認証フローに従う。

平文パスワードを画面へ再表示しない。

ログやエラーメッセージへパスワードを出力しない。

## 16. 店舗別シフトパターン管理

シフトパターンは店舗ごとに管理する。

最低限、以下を編集できる。

- コード
- 勤務時間数
- 表示順
- 使用可否

勤務時間数は、画面では時間・分で入力してもよいが、DBには分単位で保存する。

例：

```text
7時間30分
→ 450分
```

同じコードでも店舗ごとに異なる勤務時間を設定できる。

使用済みシフトパターンは物理削除せず、`is_active = false`またはSoft Deleteで扱う。

無効なパターンは新規入力ボタンに表示しない。

既存シフトと公開済みシフトのコード・勤務時間は、パターン変更により自動変更しない。

## 17. スクロール

- ヘッダー行の固定
- スタッフ名列の固定
- 表本体だけの適切なスクロール
- 日付列とシフトセルの位置一致
- 固定領域とスクロール領域の列幅一致
- スクロール中の警告表示の視認性

以下の問題を発生させない。

- スタッフ名列が日付列の下へ潜る
- 固定ヘッダーと本文の列幅がずれる
- 横スクロール時に日付とセルがずれる
- ページ全体が不自然に横スクロールする
- JavaScript実行後にスクロール位置が勝手に先頭へ戻る
- 自動保存のたびに表が再描画され、操作位置を失う

## 19. エラー表示

DB接続エラー、権限エラー、保存エラー、配布エラー等が発生した場合に、SQL、スタックトレース、秘密情報を画面へ表示しない。

ユーザー向けには、次の行動が分かるメッセージを表示する。

例：

```text
保存に失敗しました。入力内容は画面に残っています。再試行してください。
```

```text
この店舗を編集する権限がありません。
```

```text
シフトに修正が必要なため配布できません。
```

HTTPステータスは適切に使い分ける。

- 401：未認証
- 403：権限なし
- 404：対象なし
- 409：競合
- 422：入力不備
- 500：サーバーエラー

## 21. 実装方針

### 21.1 Blade

共通化により、参考画像のレイアウトやDOM構造を不必要に変更しない。

### 21.2 CSS

既存CSSとCSS変数を優先して使用する。

以下を追加しない。

- Bootstrap
- Tailwind CSS
- Bulma
- その他のCSSフレームワーク

以下を避ける。

- 大量のインラインstyle
- 不要な`!important`
- 同じ責務のクラス重複
- 画面全体の無関係なCSS全面書き換え

Vanilla JavaScriptを使用する。

以下を追加しない。

- Vue
- React
- Alpine.js
- jQuery
- npmビルドを必須にする依存関係

- Service呼び出し
- ViewまたはJSON返却

シフト保存、重複判定、人数判定、配布、公開版置換はService等へ分離する。

複数テーブルを更新する処理はトランザクションを使用する。

- `_ng`画像を実装失敗の例として扱う
